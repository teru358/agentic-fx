# 操作 API と `afx ctl` の運用 (2026-10-09)

同じマシンから稼働中の afx daemon を操作する UDS API と、同梱 CLI `afx ctl` / 鍵管理 `afx keys` の運用手順。設計の正は [操作 API 設計](../superpowers/specs/2026-10-04-ops-api-design.md)。常駐のさせ方は [afx-service-direct-exec.md](afx-service-direct-exec.md) を参照。

<a id="cli-placement-principle"></a>

## CLI の置き場の原則

daemon の生きた状態が要るなら `afx ctl`、要らないなら最上位 `afx` に置く。横断的に状態を見せる `ctl status` も、正所属は「稼働観測・実行追跡」の 1 つだけである。

| 群 | `afx`（daemon 不要） | `afx ctl`（稼働 daemon） |
|---|---|---|
| 導入・接続管理 | `[変更]` `afx init` / `[読取]` `afx check` / `[変更]` `afx check backend` / `[読取]` `afx completion bash` / `[変更]` `afx keys init`・`enroll`・`rotate`・`revoke` / `[変更]` `afx ops <feature> enable`・`disable`・`web reconfigure` / `[読取]` `afx ops <feature> status` | `[読取]` `afx ctl whoami` |
| 稼働観測・実行追跡 | `[読取]` `afx status` | `[読取]` `afx ctl status`・`log`・`activity`・`events`・`jobs get` / `[変更] [確認]` `afx ctl jobs cancel` |
| 市場入力を整える | `[変更]` `afx history import` / `[読取]` `afx history compare`・`coverage` / `[読取]` `afx news list`・`test` / `[変更]` `afx news add`・`enable`・`disable` | — |
| 調査・評価する | `[変更]` `afx backtest run`・`analyze corr` | — |
| 問い合わせ・改善運用 | — | `[変更]` `afx ctl ask`・`afx ctl improve`・`afx ctl backlog add`・`afx ctl backlog reject`・`afx ctl backlog reopen`・`afx ctl backlog note`・`afx ctl policy add`・`afx ctl policy remove`・`afx ctl policy reconcile`・`afx ctl reflect retry` / `[読取]` `afx ctl backlog list`・`afx ctl policy show` |
| Plugin を採否・配備する | `[変更]` `afx plugin submit`・`afx plugin bless`・`afx plugin materialize`・`afx plugin lock` / `[変更] [確認]` `afx plugin retire`・`afx plugin disable`・`afx plugin rollback`・`afx plugin revoke` / `[読取]` `afx plugin versions`・`afx plugin list` | `[読取]` `afx ctl approval list`・`afx ctl approval show` / `[変更] [確認] [approver]` `afx ctl approve`・`afx ctl reject`・`afx ctl approval retry` |
| 保護状態を回復する | — | `[読取]` `afx ctl killswitch reset` / `[変更] [確認] [approver]` `afx ctl killswitch reset <generation>`・`killswitch reconcile`・`data resume` |

ラベルは `[読取]`（状態を変えない）、`[変更]`（状態を変える）、`[確認]`（端末確認が必要）、`[approver]`（approver principal が必要）である。API の認可軸では、通常の状態読取は `status.read`、日常の変更は `operate`、承認判断は `decide`、資金保護の回復は `local_guard` に対応する（ほかの読取 scope は各 route 表に従う）。

API に発注・SL 変更・クローズ・サービス停止は無い。

## 1. 前提と有効化の条件

- 設定 `api.enabled` の既定は **true** (2026-10-12 裁定、初期設定ウィザード設計 P16 / 段 8)。明示的に false にした daemon は起動を拒否せず、listener を開かずに次の警告を出すだけで、取引と資金保護はそのまま動く。
  - 技術ログ: `operations API is disabled (api.enabled=false); listener not opened`
  - activity: `api_disabled`
- 前提は改善 CLI の隔離 (admission) が有効なこと。隔離が `sandbox_unavailable` のときは improve が止まるだけで、API は開いてよい (設計 §1.2 は 2026-10-12 の裁定で改訂)。
- `api.enabled` は bool の `true` だけを有効とみなす。`"true"`・`1`・`yes` では開かない。
- listener は `data/run/api.sock` (dir 0700 / socket 0600) の UDS だけ。TCP listener は作らない。
- listener を開けなかった場合 (socket path に通常 file がある、鍵集合が commit されていない、起動時回復に失敗した等) も daemon と資金保護 tick は続き、health latch・activity (`api_start_failed`)・通知に理由の固定語が残る。

## 2. 鍵

### 2.1 場所と権限

| 対象 | 場所 | 権限 |
|---|---|---|
| 鍵 dir | `~/.config/agentic-fx/api/<instance_id>/` (`instance_id` は root の実 path の SHA-256 先頭 16 桁。root ごとに鍵が分かれる) | 0700 |
| operator 鍵 | `operator.token` | 0600 |
| approver 鍵 | `approver.token` | 0600 |
| 外部 client 用の鍵 (enroll したものだけ) | `ops-bot.token` / `ops-web.token` / `ops-notify.token` | 0600 |
| 鍵集合の commit marker | `.ready` (登録済み principal ごとの世代・状態・鍵 digest) | 0600 |

- 鍵は 256 bit の乱数。daemon は起動時に読んで digest だけを持ち、env・argv・子 process の env・ログ・activity・応答には出さない。
- symlink・所有者違い・0600 以外の鍵 file は読まず、その principal だけ無効になる (他の principal は動く)。
- 鍵 dir は plugin worker・改善 worker・gate pytest worker の隔離 (Landlock) から届かない。利用者 shell と trade worker (Landlock なし) からは読める。後者は信頼境界の内側として扱う (8 節)。
- `afx ctl` と `afx keys` は `.env` を読まない。

principal と権限 (scope) の対応は次のとおりで、設定では変えられない。`autopilot on`・発注・サービス停止はどの principal にも無い。

| principal | 用途 | できること |
|---|---|---|
| `operator` | 同梱 CLI の既定 | 閲覧 (status・events・承認一覧と詳細・log / activity・`guidance.read` の backlog / policy)、自分の job、日常操作 (ask・improve・backlog・policy・reflect retry) |
| `approver` | 同梱 CLI の `--as approver` | operator の全部 + plugin の approve / reject / retry + kill switch 解除・reconcile・data resume (UDS のみ) |
| `ops-bot` | 外部の通知 bot | 閲覧 (status・events・承認一覧と詳細)、plugin の approve / reject / retry と、その job の polling / 取消。log / activity・`guidance.read`・日常操作・kill switch 系は不可 |
| `ops-web` | 読み取り専用の web | 閲覧 (status・events・承認一覧と詳細・log / activity) だけ。`guidance.read` は不可 |
| `ops-notify` | 通知 | events の閲覧だけ。`guidance.read` は不可 |

- `afx ctl` が使う principal は operator と approver だけ。`ops-bot` / `ops-web` / `ops-notify` は外部 client 用で、使うときだけ 2.4 節の enroll で鍵を作る。
- `ops-bot` は Discord 利用者を `X-Afx-Asserted-Actor: discord:<17〜20 桁の user ID>` で申告できる (他の principal が送ると 400)。決定の作成とその job の polling / 取消では必須で、作成時と違う値の polling / 取消は 403。申告値は監査 (`ops_requests.asserted_actor`) と job の所有者に記録するだけで、権限と `decided_by` (`api:ops-bot`) は変えない。

### 2.2 初回の作成

daemon が `api.enabled=true` で起動したとき、`.ready` が無ければ初版の鍵を作る。手で先に作る場合は daemon の停止中に:

```bash
cd ~/project/agentic-fx
afx keys init
```

作成済みなら何もしない。init が作るのは operator と approver の 2 本だけ。`.ready` ができた後に鍵 file が欠けた・digest が合わない・enroll / rotate / revoke の途中で止まった状態は自動で補わず、daemon は listener を開かない (`api_start_failed` / `ready_not_committed` 等)。

### 2.3 鍵 command は停止中だけ

`afx keys init|enroll|rotate|revoke` は `data/instance.lock` を取れる停止中だけ動く。稼働中に打つと「サービスが稼働中です。停止してから実行してください (無変更)」で rc=1、鍵 dir は変わらない。online で鍵を入れ替える口は無い (停止まで旧鍵が有効)。

### 2.4 外部 client 用の principal を登録する (enroll)

`ops-bot` / `ops-web` / `ops-notify` の鍵は init では作らない。使う principal だけ、daemon の停止中に登録する:

```bash
cd ~/project/agentic-fx
afx keys enroll ops-bot
```

- 未登録の principal に世代 1 の鍵を作る。operator / approver など他の principal の鍵 file・digest・世代・mtime は変えない。
- 登録済み (active) の principal への enroll は何もせず成功する (「登録済みです (無変更)」)。
- revoke 済みの principal は enroll で戻せず `invalid_state` で rc=1。戻すときは `afx keys rotate <principal>`。
- 途中で止まった (「失敗しました (…)」・daemon が `ready_not_committed`) ときは、同じ `afx keys enroll <principal>` を停止中に再実行して完了させる。その残骸の上で別の key command (別 principal の enroll や rotate / revoke) を打つと `invalid_state` で拒否され、dir は変わらない。
- 登録後に daemon を起動すると、その principal の鍵が使えるようになる。

### 2.5 `.ready` の形式

`.ready` は `{"version": 2, "principals": {<principal>: {"generation", "state", ...}}}` で、登録済みの principal だけを持つ。`state` は `active` (鍵 digest `sha256` を持つ)・`preparing` (途中。`op` に `enroll` / `rotate` / `revoke`)・`revoked` のどれか。map に無い principal は未登録で、それを理由に listener を閉じない。知らない principal 名があれば `ready_invalid` で listener を開かない。

旧形式 (`"version": 1`、operator と approver の 2 本だけ) はそのまま読める。読むだけでは書き換えず、最初に成功した鍵変更 (enroll / rotate / revoke) で version 2 に書き換わる。手で書き換えない。

repo root (afx を動かしている root) を cwd にして打つ。`afx ctl` は daemon の instance lock の保持者と socket の相手 (SO_PEERCRED・pidfd) が一致することを確かめてから鍵を送る。確かめられなければ鍵を送らず rc=3。

### 3.2 principal と端末確認

- 既定の principal は operator。approver 操作は `afx ctl --as approver <操作>` で打つ。operator のまま approver 操作を打つと何も送らず rc=3。
- 確認の要る操作 (上の表で確認欄があるもの) は **stdin と `/dev/tty` の両方が端末のときだけ** 送る。pipe・cron・スクリプトからは送らず rc=2。`--yes` は無い。
- 端末確認は誤操作を防ぐためのもので、鍵を持つ process や pty を自動化した操作を人間だと保証するものではない。
- Ctrl-C しても受理済みの job は続く。queued の間だけ `jobs cancel` で取り消せる。

### 3.3 終了コード

| rc | 意味 |
|---|---|
| 0 | 成功 |
| 1 | 業務上の失敗 (決定済み・状態不一致・取り消し・plugin 使用中など)。daemon には届いている |
| 2 | usage の誤り、または確認の要る操作を端末なしで打った (何も送っていない) |
| 3 | 接続できない・鍵を読めない・認証できない (401)・権限が無い (403)・接続先を daemon と確認できない (何も送っていないか、受け付けられていない) |
| 130 | `events --follow` を Ctrl-C で止めた |

socket が無いときの文面は「サービスに接続できません: socket がありません (…)。afx が稼働中で api.enabled=true か確認してください」。401 のときは「鍵の交換後は daemon を再起動してください」と出る。

### 3.4 backlog と policy

バックログの追加は `afx ctl backlog add <idea>`、一覧は `afx ctl backlog list [--all] [--limit N]` を使う。既定では開いている項目を表示し、`--all` は全 status、`--limit N` は表示件数を指定する。

方針文は DB の managed 行と、`policy/directives.md` の marker 外にある unmanaged 行に分かれる。旧形式のファイルは最初の投影照合で 1 回だけ移行され、DB に対応する行は ID marker 付き managed block へ再構成される。手書き行と legacy 行は unmanaged のまま保持される。

`afx ctl policy show` は純粋な読取で、DB、投影 file、監査、activity を書き換えない。`projection` は `ok`、または `stale` と固定理由語を表示する。`stale` は修復済みを意味しないため、投影を DB に合わせる明示操作は `afx ctl policy reconcile` である。成功時は `policy reconcile: changed` または `policy reconcile: unchanged` と表示する。

`afx ctl policy remove <id>` は managed row の ID を受け取る。削除できるのは ID marker 付きの managed 行だけで、marker 外の手書き行と legacy 行は削除できない。`policy show` の「管理外」表示はこの制約を示すものであり、手編集した行を API から消す操作ではない。

ops の機能操作は `afx ops <feature> enable|disable|status` の新形を使う。たとえば `afx ops web enable`、`afx ops web disable`、`afx ops web status` である。web の設定だけを変える操作は `afx ops web reconfigure`（別名 `reconf`）である。

## 4. events の cursor

- `afx ctl events` は前回の続きから表示する。位置は `~/.local/state/agentic-fx/<instance_id>/events.cursor` に「位置 high_watermark」の 1 行で保存し、表示してから進める。同じ event が再配送されても event id で 1 回だけ表示する。
- `--after <id>` を付けたときは **閲覧専用** で、保存した cursor を動かさない (過去を覗いても次回の続きは変わらない)。
- daemon 側の high watermark が前回より後退していたら、cursor を進めずに rc=1 で止まり、cursor file のパスを示して削除を促す。DB を戻した等で後退した場合は、そのファイルを削除してから打ち直す (先頭から表示し直す)。`--after` 付きの閲覧ではパスの案内は出ない。
- event は通知用の投影で、生成は best-effort。欠けた event は監査 (`ops_requests`) と業務の表を突き合わせてしか復元できない。

## 5. approve / reject / retry の表示

- approve / reject / retry は job として受け付けられ、`afx ctl` は終端まで poll して結果を表示する。
- **「approved」と表示するのは job の outcome が `deployed` または `deployed_after_rollback` のときだけ。** それ以外で done になった場合は「処理が完了しました (outcome=…)」と言い、承認したとは言わない。失敗して結果があるときは、approve なら「今回の操作では承認されませんでした (status=… outcome=…)」、retry なら「再試行は完了しませんでした」。
- reject も、確認の前に承認の内容 (detail) を表示する。id の打ち間違いに気付けるようにするため。
- 承認の内容 (`afx ctl approval <id>`、approve / reject / retry の確認前の表示) には「変更内容」の節が付く: plugin 名・kind、分類 (新規 / 更新 / 同一版 / 不明)、候補と比較対象の hash の先頭 12 桁、params の差分。diff の全文は web の承認 #N ページで読む (CLI には出さない)。内容を取得・検証できないときは固定の文だけを表示する。値は共通の redactor を通り、機微情報の可能性があるものは伏せられる。
- 引数の範囲: `log` / `activity` の n は 1〜500、`approval list` の n は 1〜200、`events --limit` は 1〜500。範囲外は鍵を読む前・接続する前に usage (rc=2)。

## 6. 鍵漏洩時の手順

鍵が漏れた・漏れた疑いがあるときは、daemon を止めてから鍵を替える。**停止中も資金保護は既存の kill switch の latch で維持し、鍵の交換のために guard (kill switch の解除・data resume) を緩めない。**

1. daemon を止める: `systemctl --user stop afx` (SIGTERM)。止まったことを `systemctl --user status afx` で確かめる。
2. 鍵を替える (repo root で):
   - 漏れた principal を使い続けるなら `afx keys rotate <principal>` (旧鍵は無効、新鍵を作る)
   - 権限そのものを止めるなら `afx keys revoke <principal>` (以後その principal は常に 401)
   - **rotate の途中で止まった残骸がある場合は、先に同じ `afx keys rotate <principal>` を打って完了させてから revoke する。** 準備状態の上で別の command (rotate の残骸に revoke、revoke の残骸に rotate) を打つと `invalid_state` で拒否され、dir は変わらない。
3. 漏れた鍵で承認・配備された plugin があるかもしれないときは、**daemon を停止したまま** 7 節で回収する。回収が済むまで daemon を起動しない (誤承認された plugin を読み込ませないため)。回収するものが無いと確かめられたときだけ、次へ進む。
4. daemon を起動し、旧鍵が拒否されることを確かめる。旧鍵での要求は 401 になる。
5. rotate したなら、同梱 CLI が新鍵を読めることを確かめる: `afx ctl --as <principal> whoami` が `principal: <principal>` を返す。

`afx keys` が「失敗しました (…)。同じ command の再実行で準備状態から完了させてください」で止まった、または daemon が `ready_not_committed` で listener を開かない (`.ready` と鍵 file が一致しない) ときは、途中で止まった command と同じ command を停止中に再実行して完了させる。`.ready` を手で書き換えたり、旧鍵に戻したりしない (自動補完も巻き戻しもしない設計)。

漏洩した鍵で既に承認・配備された plugin の回収は 7 節で、手順 3 の位置 (daemon の停止中) に行う。設計 §3.2 の「既存の運用手順」はこの節を指す。

## 7. 承認済み plugin の回収

6 節の手順 1〜2 (daemon の停止、鍵の rotate / revoke) を済ませた後、**daemon を停止したまま** name ごとに次を行う。これらは操作 API や `afx ctl` の操作ではなく、人間が実行する `afx plugin` 操作である。

1. `afx plugin versions <name>` で live、各版の承認時刻・承認者・revoke の有無、整合、経歴、未完 (open) と要注意 (closed attention) の op を確認する。疑わしい承認の時刻帯は鍵の漏洩時刻から割り出す。
2. 外す前に `--dry-run` で戻り先と影響を確認する (例: `afx plugin rollback <name> --to <hash> --revoke --dry-run`)。
3. 実行する。
   - 前の検証済み版へ戻すなら `afx plugin rollback <name> --to <hash> --revoke`。
   - 前の版が無い、又は疑わしい版を外すだけなら `afx plugin disable <name> --revoke`。
   - 既に revoke なしで外した版は `afx plugin revoke <name> --version <content-hash-prefix>`。識別子は小文字 hex の content hash 前方一致で、12 桁以上である。
   - indicator の依存 strategy が表示されたときは、意図して外す場合だけ `--force` を使う (依存 strategy の signal は止まり、pending は放棄される)。そうでなければ strategy 側を先に処置する。
   - legacy plain 配備は `afx plugin retire <name>` を使い、disable / rollback は使わない。
4. 版 dir は消えない。調べたい版は `plugins/.versions/<name>/<hash>/` を読み取り専用のまま保全する。コピーを取るなら `data/` の外へ置く。保全の前にディスクの空き容量を確認する。版 dir を手作業で削除しない。
5. 全 name の回収が済んだら daemon を起動し、`afx ctl --as <principal> whoami` と旧鍵の拒否 (6 節手順 4〜5) を確かめる。続けて `afx plugin versions <name>` の live と op の状態が意図どおりか、`afx ctl status` の `plugin_deploy_ops` 節 (`open` / `attention`、読めないときは `unavailable`) と `afx ops <feature> status` (未完 op が 1 件以上のときだけ 1 行) を確認する。

未完 (open) と要注意 (closed attention) の op の扱い:

- 未完 (open): `needs_retry/syscall_failed` は権限・mount・ディスクなどの原因を直した後、**同一署名の command** (`--revoke` / `--force` / `--to` を変えない) を再実行する。
- 要注意 (closed attention): `needs_retry/verify_failed` は op としては閉じている。live は不在なので、原因を直した上で新しい `rollback --to` 又は `disable` を実行する。
- 既存の open op の再実行や daemon 起動時の reconcile で lock を待ち切れなかった場合、op は open のまま残り、`versions` と status の未完表示に出る。新規操作の lock 待ち超過は op を作らない。

`foreign` は専用コマンドでは回復しない。`versions` で live を確認して分類する。

| live | 手順 |
|---|---|
| symlink、又は live 不在 | `versions` で版 dir の整合と承認を確認し、検証済みの版を bless / approve する。 |
| plain | 外部データを保全し、必ず `retire` を経てから bless / approve する。 |
| 不明又は改変 | daemon を停止し、証跡を保全してから調査する。 |

rollback の戻り先は daemon を起動するまで反映されない。activity は通知試行なので、回収の判定は `versions` と status の状態を正とする。

## 8. 既知の制限

- **単一利用者のホストが前提**: 既定の web (自機のみ・認証なし) は、承認 #N に plugin の diff 全文 (取引ロジック) を出す。同じホストの他の利用者はこれを読める。秘密 (鍵・口座・URL など) は共通の redactor が伏せるが、戦略そのものは見える。diff の伏せ字は、表示値に字面として現れる値に限られ、複数の断片や `chr()`・encoding から再構成される値は伏せない (改善 agent の入力に実ホスト名・秘密が無いことを前提に受容している)。複数の利用者が使うホストでは web を有効にしない。LAN へ公開する場合の範囲と残余は 10 節。
- **同じ uid の隔離されていない process**: 利用者 shell と trade worker は鍵を読めるので、そのどちらかを侵害した攻撃者からは鍵も `local_guard` (kill switch 解除・reconcile・data resume) も守れない。daemon の子 process からの直接の要求は 403 で拒否するが、二重 fork して子孫判定を外れた process は通る (既知の限界。主防御は隔離された文脈から鍵が読めないこと)。trade worker の Landlock は別チケット。
- **同 uid の偽 server**: 本物の daemon の停止中に攻撃者が instance lock も取ると、`afx ctl` の接続先確認を突破できる。
- **鍵の一時 file の孤児**: 新鍵を置く command (`afx keys init`・`enroll`・`rotate`、および起動時の初回補完) が新鍵の一時 file (`.<principal>.token.<乱数>.tmp`) を書いてから rename / link するまでの間に SIGKILL・電断で止まると、平文の一時 file が鍵 dir に残る。鍵 dir は 0700 なので露出は増えず、残った一時 file の鍵は `.ready` に載らないので認証には使えない。ただし再実行は別名の一時 file を作るので、古いものは消えずに残り続ける。`.ready` の一時 file (`..ready.<乱数>.tmp`) と revoke の tombstone の一時 file (名前は鍵と同じ形) も同じ理由で残り得るが、こちらは秘密を含まない。チケット `ops-keys-orphan-secret-temp-after-hard-crash`。
  - **掃除の手順** (daemon 停止中に行う。稼働中は鍵 command 自体が断られる):
    1. `systemctl --user stop afx` で daemon を止め (`systemctl --user status afx` で確認)、`afx keys` も走っていないことを確かめる。
    2. 止まっていた command があれば、同じ command を再実行して完了させる (6 節)。
    3. 鍵 dir (`~/.config/agentic-fx/api/<instance_id>/`) で `ls -la` し、`.<principal>.token.*.tmp` と `..ready.*.tmp` だけを削除する (例: `rm -- ~/.config/agentic-fx/api/<instance_id>/.*.token.*.tmp ~/.config/agentic-fx/api/<instance_id>/..ready.*.tmp`、該当が無ければ rm は「存在しない」と言うだけ)。`<principal>.token` と `.ready` 本体は消さない。
    4. daemon を起動し、`afx ctl --as operator whoami` が応答することを確かめる。
- **再起動で消えるもの**: job は memory 上なので daemon の再起動で消える。受理と終端は `ops_requests` に残り、終端の無い受理は次の起動で `outcome_unknown` になる (成功らしく見えても成功とは記録しない)。現状態は `status`・`approval <id>` で確かめる。
- **増え続けるもの**: `ops_requests` と `ops_events` は無期限保持。`activity.log` に rotation は無い (`activity-log-grows-without-rotation`)。
- **plugin lock の待ち**: 操作 API の decision は `plugin_busy` を返す。deploy CLI の lock 待ちは別契約で、30 秒超過時は `lock_timeout`（rc 1）となる。両者を同じ状態として扱わない。

## 9. 取引通知の設定 (bot / notify の `ops.toml`)

発注 (`order_state_changed`) と決済 (`position_closed`) の event を bot が日本語の短い文にして投稿する。設計の正は [発注・決済の通知 設計書](../superpowers/specs/2026-10-20-trade-notices-design.md)。設定は機能ごとの `ops.toml` (`$XDG_CONFIG_HOME/agentic-fx/ops/<feature>/config/ops.toml`) の optional な平坦 key 3 つだけで、**key が無い旧 `ops.toml` のままで新しい afx-ops が起動する** (既定値になる)。不正な値は起動時に拒否される (probe も `config_invalid`)。値を変えたら bot / notify を再起動する (起動時に 1 回だけ読む)。

| 機能 | key | 値 | 既定 | 働き |
|---|---|---|---|---|
| bot | `trade_notices` | `all` / `results` / `fills_closes` / `off` | `all` | 投稿する種類。`results` = 約定・拒否・決済、`fills_closes` = 約定・決済、`off` = 取引通知を出さない。出さない event も cursor は進む |
| bot | `trade_amounts` | `absolute` / `relative` | `absolute` | 文面の数値。`relative` は数量と損益の絶対額を出さず、R 倍数と価格の変化率 (%) だけを出す。出す種類は変えない |
| notify | `deliver_trade_events` | `true` / `false` | `false` | webhook に取引 event を配送するか。false のときは配送せず cursor を進める。既存の承認・改善・health の event には影響しない |

```toml
# bot の ops.toml に足す例 (結果系だけを、絶対額なしで出す)
trade_notices = "results"
trade_amounts = "relative"
```

- 取引通知には、設定済みの `mention_role_id` / `mention_user_ids` を**付けない** (本文からも mention は発生しない)。承認通知と既存の event 通知の mention は従来どおり。
- `trade_amounts = "relative"` でも、event と webhook には `qty` と `pnl` が残る。webhook に流したくないときは `deliver_trade_events` を false のままにする。
- event の値が決められた書式 (field ごとの固定書式の文字列) でない、または未知の event code のときは、bot と notify は投稿せず cursor を進めずに止まる (`payload_invalid`)。項目だけを省いた投稿はしない。
- **戻すとき**: `trade_notices = "off"` は bot の表示の絞り込みで、daemon は取引 event を出し続ける。daemon の emitter を止めずに afx-ops だけを古い版へ戻すと、新しい event で bot と notify が止まる。戻す順序は設計書 §10.3 に従う (emitter を止める → bot と notify の cursor が追いついたことを確認 → afx-ops を戻す)。

## 10. web の公開範囲 (自機のみ / LAN / allow / パスワード)

同梱の web は読み取り専用のまま、待受先・接続元・認証を利用者が選べる。**既定は自機のみ (`127.0.0.1`)・認証なし**で、緩めるのは利用者の明示操作と自己責任である。nginx や SSH 転送は要求しない。

### 10.1 設定の 3 軸とユーザー名

web の `ops.toml` (`~/.config/agentic-fx/ops/web/config/ops.toml`) は `port` に加えて次の 4 key を持つ。どれも省略でき、省略は「自機のみ・認証なし (ユーザー名は `afx`)」を表す。

| key | 値 | 意味 |
|---|---|---|
| `bind` | 本機の up な interface にある具体的な IPv4 | 待ち受ける address。`0.0.0.0`・hostname・IPv6 は使えない |
| `allow` | IPv4 / CIDR の list | 接続元の制限。**LAN の `bind` では必須**。無制限は省略ではなく `["0.0.0.0/0"]` の明示 |
| `auth` | `"none"` / `"basic"` | `basic` はユーザー名 `user` と `web.password` (secret dir 内) |
| `user` | 英小文字で始まる 1〜32 文字 (英小文字・数字・`_`・`-`) | Basic 認証のユーザー名。省略時は `afx`。`auth = "basic"` のときだけ書かれ、`afx` でも省略されない。`:`・大文字・改行・33 文字以上は `config_invalid` |

`web.password` は **8〜32 文字**の可視 ASCII (`:` を含められる。空白・改行・非 ASCII は不可)。生成値は 22 文字。以前の版で作った 33 文字以上の password は `secret_invalid` で止まる。直すには、web が止まっている間に `web.password` を手で削除し、そのあとで `afx ops web reconfigure` を実行する (対話なら「再設定」、非対話なら `--secret-action install --password-file <file>`)。reconfigure は不安全な既存の password を置き換えない。止まるときの案内文は `旧版の 33 文字以上の password は、停止中に web.password を削除してから afx ops web reconfigure を再実行する` である。所有者・mode・型・文字種・長さが不安全な `web.password` は、自動では直さない。

本体と `afx-ops` は同じ checkout の版を使う。版がずれると fail closed になる: 新しい本体が書く `user` を古い `afx-ops` が未知の key として拒むと `config_invalid`、古い `afx-ops` の `interfaces` の出力 (version 1) は `interface_lookup_failed` になる。

| 運用形 | `bind` | `allow` | `auth` |
|---|---|---|---|
| 自機のみ (既定) | `127.0.0.1` | 省略 | `none` |
| LAN・許可 IP だけ | LAN の IPv4 | 限定した IPv4 / CIDR | `none` |
| LAN・パスワードだけ | LAN の IPv4 | `["0.0.0.0/0"]` | `basic` |
| LAN・両方 | LAN の IPv4 | 限定した IPv4 / CIDR | `basic` |
| LAN・到達できる全 IPv4 | LAN の IPv4 | `["0.0.0.0/0"]` | `none` |

`auth = "none"` のまま安全な `web.password` が残っていると、起動も probe も `secret_unexpected` で止まる (認証済みのつもりで無認証公開する事故を避けるため)。`auth = "basic"` で password が無ければ `secret_missing`。

### 10.2 有効化と質問

`afx ops web enable` は端末から次を順に尋ねる (設定が揃っていれば、まず要約 1 行と、`この設定で有効化します。[1] このまま [2] 変更する` の 1 問だけ)。角括弧の中は空 Enter で採られる初期値で、「既定」とは書かない (例: `port [8788]:`)。

1. `port [8788]:`
2. `公開範囲 [1] 自機のみ [2] LAN [1]:`
3. LAN なら、`この PC のどの IP アドレスで待ち受けるかを選んでください（他の PC はこのアドレスにアクセスします）。` と表示してから待受 address を選ぶ。候補は `afx-ops interfaces` が返す global / link の IPv4 で、`192.168.1.30 (enp6s0)` のように interface 名を添える (複数なら明示選択。手入力はできない)
4. `アクセス制限 [1] 許可 IP [2] Basic 認証 [3] 両方 [4] なし (到達できる全 IPv4) [1]:`
5. Basic 認証 (又は両方) を選んだとき、安全な既存の `web.password` があれば直ちに `現在の Basic 認証を [1] 維持する [2] 再設定する` を尋ねる。維持はユーザー名とパスワードを変えず、表示もしない
6. 許可 IP (又は両方) なら許可する IPv4 / CIDR (空回答は再質問)
7. 再設定 (又は既存の password が無いとき) は `ユーザー名 [afx]:` (既存の設定があればその値が初期値)、続けて `パスワード (空 Enter で自動生成):`。空 Enter なら 22 文字の値を生成する。手入力 (8〜32 文字) なら直後に `もう一度:` で同じ値を確認する。ユーザー名・パスワードの文法違反と不一致は合わせて 3 回目で `setup_aborted` になり、何も書かない

生成した password は**保存が終わった後に 1 回だけ**、`ユーザー名: <user> / 生成した password (この表示は 1 回だけです): <password>` の形で表示される。再実行では再表示しない。

「なし (到達できる全 IPv4)」を選ぶと「LAN、VPN、port-forward 等を含め、このアドレスへ到達できる全 IPv4 source が戦略の diff を読めます」と表示し、`yes` と入力しない限り何も書かない。

要約は stderr に 1 行で出る。公開の欄は `自機のみ` / `許可範囲 <N> 件` / `到達できる全 IPv4`。allow の中身と password は含まない。

```
web: 待受 <bind>:<port> / 公開 <範囲> / 認証 none
web: 待受 <bind>:<port> / 公開 <範囲> / 認証 basic (<user>)
```

- `afx ops web enable --ask` は未設定または disable 後の新規 enable だけで使え、既存値を既定として全項目を再質問する。有効化済みでは `already_enabled` で何も変えず、`設定の変更は afx ops web reconfigure` と案内する。
- `afx init` を再実行しても、web が未設定または disable 後で設定が揃っていれば、この要約と 1 問が出る。有効化済みなら何も尋ねない。
- 端末が無い実行 (`--non-interactive`、又は TTY 無しで設定が揃っているとき) は質問せず要約だけを出す。

### 10.3 非対話

```
afx ops web enable --non-interactive --config-file <目標の設定> --secret-action <remove|keep|install|absent> [--password-file <file>]
```

`--config-file` は `port`・`bind`・`allow`・`auth`・`user` の 5 key だけの TOML (共通 key は書かない。`user` は省略すると `afx`)。自分の所有で group / other に書込み権が無い通常 file (mode `0644` か `0600`)、1〜65536 byte。`--password-file` は自分の所有・mode `0600` ちょうどで、可視 ASCII 8〜32 文字 (末尾の改行 1 個は可)。password file の path はどこにも記録しない。

| 目標の auth | 今の password | `--secret-action` | `--password-file` |
|---|---|---|---|
| `basic` | あり | `keep` | 不可 |
| `basic` | なし / あり | `install` | 必須 (置換する) |
| `none` | あり | `remove` | 不可 |
| `none` | なし | `absent` | 不可 |

表に無い組み合わせは `setup_input_required` (rc 2) で何も変えない。今の password が不安全 (所有者・mode・型・未知の file) なら `secret_invalid` で止まり、自動では直さない。

### 10.4 設定を変える: `afx ops web reconfigure`

有効化済みの web の設定 (平文 HTTP の公開範囲・到達範囲・password を含む) は、次で変える。別名は `reconf`。

```
afx ops web reconfigure
afx ops web reconfigure --non-interactive --config-file <目標の設定> --secret-action <...> [--password-file <file>]
```

- 止まるのは **ops-web だけ**で、web が数秒から十数秒見えなくなる。afx (ペーパー運用)・鍵・enable の記録には触れない。
- 手順: 入口の確認 (読み取りだけ) → 質問 → ops-web を止める → secret → config の順に反映 → probe → ops-web を止め直して起動し、READY を確かめる。`web: reconfigured` で終わる。afx が止まっているときは `web: reconfigured ops=starts_with_afx` で、次の afx 起動時に新しい設定で上がる。
- 対話では完全な既存設定でも全項目を既存値付きで尋ねる (要約の 1 問は出ない)。Basic 認証に変えるとき、既存の安全な password があれば `現在の Basic 認証を [1] 維持する [2] 再設定する` を最初に尋ねる。
- probe に失敗しても元の設定には戻さない (書いた目標のまま止まる)。固定 reason と `afx ops web reconfigure を再実行する` が出るので、直して再実行する。途中で止まっても同じ reconfigure の再実行で完結する。
- 入口で止まる主な理由と案内: `not_enabled` (有効化済みでない)、`invalid_state` (`afx ops web enable で状態を回復してから再実行する` / `systemctl --user daemon-reload の後に再実行する`)、`principal_key_mismatch` (`afx を止めて afx keys rotate ops-web を実行し、afx を起動してから afx ops web reconfigure を再実行する`)、`setup_busy` (enable・disable・別の reconfigure・`afx init` の実行中)。

**`afx ops web disable` → `afx ops web enable --ask` との違い**: こちらは enable が afx を止めて再起動するため、ペーパー運用が数十秒止まり得る。reconfigure は afx を止めない。設定だけを変えるなら reconfigure を使う。`afx ops <feature> disable` も `data/ops/setup.lock` を取り、取れなければ `setup_busy` で何も変えない。

reconfigure の途中で止まると `auth` と password の組が一時的に食い違う (`secret_unexpected` / `secret_missing`)。この間 web は起動せず (fail closed)、`afx ops web enable` でも直らない (afx を止めずに `afx ops web reconfigure を再実行する` と案内する)。直すのは reconfigure の再実行。

### 10.5 状態の確認

`afx ops web status` は stage と unit の行に続けて公開範囲を 1 行出す。

```
web-access: bind=192.0.2.10:8788 allow=restricted auth=basic user=afx
web-access: bind=192.0.2.10:8788 allow=restricted auth=none
web-access: unavailable reason=<固定 reason>
```

Basic のときだけ `user=<user>` が付く (ユーザー名は秘密ではない)。`allow` は `restricted` (0.0.0.0/0 以外)・`unrestricted` (`0.0.0.0/0`)・`loopback-default` (自機のみで allow 省略)。allow の中身・password・path は出さない。読めないときの reason は起動・probe と同じ判定の結果 (`not_configured`・`config_dir_missing`・`config_invalid`・`allow_required`・`secret_missing` など)。

### 10.6 残余リスク (利用者の責任)

- **平文 HTTP**: 同じ経路を観測・改変できる者は Basic の認証情報と表示内容を盗聴・改変できる。Basic は暗号化でも server 認証でもない。TLS は提供しない。
- **IP allowlist**: IP の偽装・ARP spoofing・DHCP の払い出し変更・NAT により、端末や人の同一性は保証できない。allow 内の侵害済み端末は到達できる。
- **到達できる全 IPv4**: LAN・VPN・port-forward を含め、そのアドレスへ届く全 source が読める。host firewall・router・container・cloud network の実効範囲は製品が検証しない。
- **生成 password の表示**: 1 回だけ端末に出る。画面共有・scrollback・肩越しの観察から漏れ得る。
- **試行の制限**: 送信元別と全体の失敗回数の窓は process 内の状態で、再起動で消える。時間を空けた攻撃や複数 host からの総当たりは防げない。全体の窓に達すると正しい利用者も最大 60 秒入れない。
- **flood と slowloris**: allow 外の接続は早期に切るが、回線や CPU を飽和させる DoS は防げない。allow 内の source が接続枠を占有して正規の要求を一時的に妨げ得る。
- **port の競合**: probe は port を予約しない。probe の後に別の process が取ると本番の起動は fail closed になり、start-limit に当たって再試行が止まり得る。回復は `afx ops web reconfigure` (起動前に ops-web の `reset-failed` を送る)。
- **address の変化**: DHCP などで待受 address を失うと `bind_not_local` / `probe_bind_failed` で止まる。自動で別 address へ広げない。利用できる address を選び直す `afx ops web reconfigure` で回復する。
- **iproute2 への依存**: LAN の待受候補は `ip -j addr show up` に依存する。無い・版の違いで読めない環境では LAN の bind を `interface_lookup_failed` で拒否する (自機のみは影響しない)。
- **読み取り専用の限界**: 変更権限は無くても、損益・稼働状態・ログ・承認の詳細・戦略の diff は機密である。
