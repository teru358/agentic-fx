# 設計: ohlcv キャッシュ・フォールバックの整合性と配線 pin

**位置づけ**: プラン 9 の task として実装する。本書はその spec。
**日付**: 2026-08-10
**出自**: C3 調査 (`.superpowers/sdd/2026-08-04-phase2-8-worker-isolation/c3-investigation.md`) の副産物。
C3 自体は「エスカレーション不要・実質解消済み」で閉じた。本書は調査で出た別の 3 件を扱う。
**裁定**: ユーザー承認済み (2026-08-10) — ②は案 A (要求期間だけ読む)、①③ と併せてプラン 9 の task。

## 1. 背景 — 何が起きているか

`PriceProvider` はライブソースが全滅したとき `_cached_bars` でキャッシュから足を作る。
**1h/4h の行は本番に存在しない** (4h は `DERIVE_ONLY_INTERVALS`、1h は yfinance では導出)
ため、`_cached_bars` は**より細かい base 足 (実運用では 1m) から導出**して復元する。
scheduler tick が `latest_1m_bar` 経由で 1m を継続的に書くので、この機構は**実際に機能する**
(実測済み)。

問題は 3 つ:

1. **`_cached_bars` は要求された期間を無視して全件を読む** — `load_bars` を
   `since`/`until` なしで呼ぶ (`price_provider.py:228`)。`store/ohlcv.py` には
   `DELETE` が一切無く保持ポリシーも無いので、1m は**無制限に蓄積**する
2. **本番の連鎖 (`1m → 1h`) を pin したテストが 1 本も無い**
3. **2 箇所のコメントが機構の肝を書いていない**

## 2. 実測

### 2.1 蓄積量に対するフォールバックのコスト

ライブ bar ソースを全て落とし、本番の readonly provider で `get_bars(pair,"1h")`:

| 1m 蓄積 | 1m 行数 | 導出 1h 本数 | 所要 | ピークメモリ |
|---|---|---|---|---|
| 1 日 | 1,440 | 25 | 0.03 秒 | 0.9 MB |
| 7 日 | 10,080 | 169 | 0.19 秒 | 6.1 MB |
| 30 日 | 43,200 | 721 | 0.83 秒 | 26.7 MB |
| **180 日** | 259,200 | 4,321 | **5.76 秒** | **161.9 MB** |

**計測の限界**: 蓄積データは**連続合成バー**である。実データの週末ギャップ下で
`validate_bars` が全期間に対しどう振る舞うかは**未検証** (§6)。

### 2.2 このコストは障害時だけではない

実環境の測定で、**ライブ健全時にも `get_bars(pair,"1h")` が `origin='cache'` で返った**
(ライブ 1h が gap 検証で落ちたため)。したがってフォールバック経路は例外時のみでなく
**平常運転で毎サイクル通りうる**。

### 2.3 不整合そのもの

`get_bars(pair, interval, lookback_days=5)` は「5 日ぶん」を要求している。
ライブ経路は 5 日ぶん取りに行くが、**キャッシュ経路だけが 180 日ぶん返す**。
これは性能の問題である前に**契約の不整合**である。

## 3. 設計

### 3.1 [②] `_cached_bars` は要求された期間だけ読む

`get_bars` は `lookback_days` を持っている (`price_provider.py:139`)。
`_cached_bars(pair, interval, now, errors)` (`:192`) に渡し、
`ohlcv.load_bars(..., since=...)` で絞る。呼び出し箇所は 1 つ (`:182`)。

#### **`since` は対象 interval の境界に floor すること (必須)**

`bars.py:91-92` が明記しているとおり **`resample` は「部分的なバケット (形成中の足) は残す」**。
したがって `since` を任意時刻で切ると、**先頭の 1h 足が部分的な 1m データから作られ、
正常な足として返る** (open が「その時刻の値」になり、真の始値ではない)。

**`since` は `BAR_ANCHOR` 格子上で対象 interval の境界へ floor する。**
これにより先頭バケットは完全になる。末尾の形成中バケットが残るのは既存挙動で、変えない。

この floor は **base 候補ごとに対象 interval の境界**で行う (base の境界ではない) —
1h を作るなら 1h 境界に floor する。

#### 効果

- DB の行数に関係なく読み込み量が一定になる
- ライブ経路とキャッシュ経路が**同じ期間**を返すようになる (契約の整合)

### 3.2 [①] 本番の連鎖を pin する

既存テストは **base を直接 seed** している (`1h`→4h、`15m`→30m) ため、
**本番の `1m → 1h` は 1 本も pin されていない**。以下の退行が全テスト green のまま通り、
症状は**ライブ全滅時にしか出ない**:

- `_base_candidates` から 1m が外れる (「取得本数が多い」等の理由でありうる)
- scheduler tick が 1m を書かなくなる / `bars_fn` の配線が変わる

**pin は配線を実際に駆動する形で置く** — 単体で base を seed するのではなく、
**tick が 1m を書くところから**始めてライブ全滅までを通す
([[verify-integration-not-just-units]])。

### 3.3 [③] コメントに機構の肝を書く

`service.py:518-523` と `mission_registry.py:54` は
「親の scheduler tick が継続的に cache を温めるため実害は限定的」とだけ書いている。
**「書かれるのは 1m だけで、1h/4h はその 1m から導出して復元される」という肝心の機構が無い。**
読者は「1h 行が書かれている」と誤読しうる (本調査で指揮者が実際に誤読した)。

## 4. 変えないもの

- **`readonly` の silent-skip** (裁定書 F-5 / CR-4 — RPC 面を拡大しない)
- 1h/4h を行として保存しない設計 (`DERIVE_ONLY_INTERVALS` / 導出足は保存しない)
- `latest_1m_bar` の `lookback_days=1` (tick の取得量)
- 末尾の形成中バケットを残す挙動
- **保持ポリシー (prune) は入れない** — §7 で起票する
- 決定論的コア

## 5. テストと変異 (検査点ごとに独立させる)

| # | 独立テスト | 殺す変異 |
|---|---|---|
| 1 | `_cached_bars` が `since` 付きで `load_bars` を呼ぶ | `since` を渡さない |
| 2 | 要求 `lookback_days` を超える古い行が結果に**入らない** | 期間の絞りを外す |
| 3 | **`since` が対象 interval の境界に floor される** | floor を外す (任意時刻で切る) |
| 4 | **先頭の 1h 足が完全である** (部分バケットが混ざらない) — 始値が真の時間始値 | floor を外す。3 とは別の観測点にする |
| 5 | 末尾の形成中バケットは従来どおり残る | 末尾も落とす退行 |
| 6 | **本番連鎖**: tick が 1m を書く → ライブ全滅 → `1h` が cache から返る | `_base_candidates` から 1m を外す |
| 7 | 同上で `4h` も返る | 同上 |
| 8 | tick が 1m を書いていること自体 | `bars_fn` の配線を切る |
| 9 | 蓄積が大きくても読み込み件数が要求期間ぶんに収まる | 絞りを外す |

**変異は 1 つずつ独立に当て、殺した固有のテスト名を記録する。**
1 テストに複数 assert を並べない — 先に落ちる assert が後続を短絡させる
(プラン 8 Task 19/20 で 2 度実測した穴)。

## 6. 未検証リスク (実装時に必ず確認する)

**実データの週末ギャップ下で、長期間の 1m に対する `validate_bars` がどう振る舞うか。**
§2.1 の計測は連続合成バーで行った。実データでは市場閉場のギャップが入るため、
全期間を検証すると gap 判定に掛かる可能性がある。掛かるなら**フォールバックが
そもそも成立しなくなる**ので、§3.1 の絞り込みは**性能改善ではなく機能の前提**になる。

実装の最初にここを実測すること。結果次第で §3.1 の位置づけが変わる。

## 7. 本 task では直さず起票するもの

**`ohlcv` の無制限増大。** `store/ohlcv.py` に `DELETE` が無く、保持ポリシーも無い。
1m は 1 ペアあたり 1 日 1,440 行 (実測 180 日で 259,200 行) 増え続ける。
§3.1 で読み込みコストは一定になるが、**DB のサイズ自体は増え続ける**。

保持期間の要件・バックテスト履歴 (`history_conn`) との関係を含む**別の設計判断**なので、
本 task には混ぜない (ユーザー裁定)。

## 8. 受入条件

1. キャッシュ経路とライブ経路が**同じ期間**の足を返す
2. **先頭の足が部分バケットにならない** (始値が真の時間始値)
3. DB の蓄積量に関係なく、フォールバックの読み込み量と所要が要求期間ぶんに収まる
4. **本番の `1m → 1h` 連鎖が、tick の書き込みから通しで pin されている**
5. §6 の未検証リスクが実測で決着している
6. 既存テストが 1 本も壊れない
