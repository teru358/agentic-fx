チケット: `weekly-improve-rebacktests-deployed-strategies`、`strategy-attribution-and-shadow-evaluation`、`weekly-plugin-inventory-notice` (3 件を 1 つの設計に束ね、4 段で実装する)。

## 0. 何が起きているか

- 配備中の戦略が、配備後にどう動いたかを戦略ごとに見る面が無い。材料 (signal の採否と、採否ごとの機械採点) は DB にあるが、戦略別に集計して出す経路が無い。

- 成績の悪い戦略を止める判断は人間がするが、判断を促す定期の知らせが無い。

## 1. 何が変わるか (動作)

### 1.1 利用者が受け取るもの

1. **いつでも (web・CLI)**
   - plugin 一覧で、指標ごとに「未使用」の印と理由が読め、未使用だけに絞れる (段 1)。
   - 戦略別の画面で、実取引の成績の隣に **機械採点** (その戦略の signal を採否にかかわらず規則どおり建てていたら) の成績、採否の件数、採点できなかった件数が並ぶ (段 2)。見出しの下に「機械採点は実約定を含まないので楽観側に出ます」「採否に至らなかった signal は含みません」を必ず出す。
2. **週に 1 回 (取引週の終わり)** (段 3)
   - 親専有の週次 report が 1 本できる。戦略ごとの判定 (下表) と数値、未使用の指標の一覧を載せる。
   - 知らせる内容があれば Discord に 1 通。「停止の提案」として、停止候補・低下の戦略 (名前と 4 項目の数値) と、未使用の指標の本数・新しく加わった名前を出す。
   - 最初の数週は判定が「標本不足」で、件数だけが出る。判定が付くのは、同じ版の採点が 30 件たまり、最初の採否から 4 週たってから。
3. **利用者が判断すること**
   - 停止候補の戦略を止めるか。止めるなら `afx plugin disable <name>`。数字を今の履歴で確かめたいなら `afx plugin reevaluate <name>` (却下すれば停止と一体)。
   - 未使用の指標を外すか。外すなら `afx plugin disable <name>` / `afx plugin retire <name>`。
   - システムは自動で止めない・外さない・消さない。提案を放置しても取引は変わらない。

| 判定 (人間向け) | 意味 |
|---|---|
| 標本不足 | 採点 30 件未満、または最初の採否から 4 週未満。件数だけを出す |
| 維持 | 直近 12 週の機械採点の平均 R が正で、直近 4 週も負でない |
| 低下 | 直近 12 週は正だが、直近 4 週 (10 件以上) の平均 R が 0 以下 |
| 停止候補 | 直近 12 週の平均 R が 0 以下 |

### 1.2 改善 agent が受け取るもの (段 4)

- **停止済みの plugin の名前** (名前と kind だけ)。同じものを別名で作り直さないための一覧。止めた理由・止めた経路 (手動、再評価の却下、提案の採用) は区別しない。
- **配備中の戦略ごとの方向の語** (`維持` / `低下` / `停止候補`、標本不足は `-`)。数値・件数・期間・続いた週数は渡さない。これは遮断の明示の例外で、利用者の裁定を要する (§6 問 4)。

### 1.3 変わらないもの

発注・SL・決済・資金保護の経路、採否の契約、shadow の採点規則、採用 gate と床、承認の流れ、`afx plugin disable` / `retire` / `reevaluate` の動作。外向きの通信先は増やさない。

## 2. 仕組み

### 2.1 段の分け方と依存

| 段 | 内容 | 依存 | 単独の価値 |
|---|---|---|---|
| 1 | 指標の棚卸し (読取面だけ) | なし | 未使用の指標を一覧で拾える |
| 2 | 戦略別の前方成績 (機械採点を人間の面に出す) | チャートの段の merge | 戦略そのものの前方成績が初めて見える。`per-strategy-virtual-books` の着手条件 (勝ち筋 2 本以上) を測れる |
| 3 | 週次の確定・判定・停止の提案 (通知) | 段 1・段 2 の集計関数 | 見に行かなくても知らせが来る |
| 4 | 改善 agent への掲示 (停止済みの名前、方向の語) | 段 3 の確定が 4 回以上 | 改善の方向づけ |

チケットの順 (帰属・影 → 定期評価 → 棚卸し) は採らない。棚卸しの読取面は成績を要らず、最も小さく、先に出せる。agent への掲示は遮断に触れるので最後に置く。3 件を別々の設計にしない理由は、週次の起動・保存・通知・人間の操作が共通だからである。

### 2.2 指標の棚卸し (段 1)

**未使用の定義。** 配備中 (live) の指標で、次のすべてを満たすもの。

1. 配備中の戦略の config.yaml から参照されていない (既存の `dependents` が空。`S/plugin/read_model.py:170,405-409`)。
2. 保留中の承認依頼の候補から参照されていない (`S/plugin/deploy_deps.py:28`)。
3. 直近 K 週に作られた改善候補の族に名前が出ない (`candidate_archives` の `family_key` と `created_at` だけを読む。族の key は依存する指標の名前を含む)。
4. その指標が配備されてから K 週以上たっている。

K の既定は 8 (§6 問 3)。条件 3・4 を置く理由は、改善 agent が候補に使えるのは配備中の指標だけで、「まだ戦略に採られていない」は「材料として不要」を意味しないからである。条件 1 だけなら今は 91 本が該当する。

**出所の扱い。** 人間が入れた指標 (承認済み依頼の `candidate_origin=human`) は一覧に印を付けて出すが、停止の提案には数えない (§6 問 3)。

**出し方。** plugin の read model の行に `inventory` (未使用か、満たした条件、最後に候補に現れた月) を足す (`S/plugin/read_model.py:573`)。web の plugin 一覧は「参照元」「提出 / 配備の回数」の隣に「未使用」を出し、絞り込みと並べ替えに使う (`A/web/plugin_pages.py:185-196`)。CLI は `afx plugin list --unused`。週の区切りと保存は段 3 まで持たない (読むたびに今の状態で判定する)。この read model を読むのは操作 API の plugin 一覧と `afx plugin` の CLI だけで (`S/ops/plugins_view.py:58-59`、`S/backtest/plugin_deploy_cli.py:113`)、改善 context は別の一覧 (`S/loops/improve_loop.py:985`) を使うので、`inventory` は agent に届かない。

### 2.3 戦略別の前方成績 (段 2)

**対象。** 配備中の戦略の、今 live の版 `(name, content_hash)`。signal は版を持つ (`S/store/db.py` の `signals.content_hash`) ので、版が替わる前の signal は混ざらない。同名で版が替わったら数え直しになる。チャートの段は名前で 1 行に合算する (設計 2026-11-19 §1.2) ので、機械採点の列には版が替わった時刻を注記する。

**前方区間。** 窓は「今から 12 週前」〜「今」。その版の signal は配備後にしか生まれないので、配備時刻を別に引かなくても配備後の区間になる。採否時刻 `signal_decisions.decided_at` で窓に入れる。

**3 つの系列を並べる (合算しない)。**

| 系列 | 中身 | 何を測るか | 単位 |
|---|---|---|---|
| 機械採点・全採否 | その版の shadow のうち数値で終端したもの (`sl` / `tp` / `day_close`)。accept と reject の両方 | 戦略そのもの (LLM の選別・枠・裁量決済を含まない) | R |
| 機械採点・accept / reject 別 | 同上を採否で分ける | LLM の選別が効いているか (accept の平均 R − reject の平均 R)。表示だけ | R |
| 実取引 | チャートの段の戦略行をそのまま使う (`W/ops/performance_view.py:867`) | 実際に動かした結果 | 口座通貨・R |

**機械採点の R。** `R = pnl_pips ÷ (|entry_price − stop_loss| ÷ pip_size)`。`stop_loss` は signal の保存値 (`signals.payload_json`)、`entry_price`・`pnl_pips`・`pip_size` は shadow 行の値。分母が 0 以下・非有限・SL 欠落は「R 不明」に数え、率の母数から外す。lot を持たない採点を pips のまま足すと SL の広い取引が重くなる。実取引は 1 取引のリスクを一定にして建てるので、R で数えるほうが実運用に近い。backtest の `avg_r` (金額の定義、`S/backtest/metrics.py:89-97`) と無条件に一致するとはしない。

**指標。** 件数 N (R 既知)、勝 / 負 / 分、平均 R、PF (R の利益合計 ÷ 損失合計)。R で数えると「PF < 1」と「平均 R < 0」は同じ条件なので、判定は平均 R の 1 本で行い、PF は表示にだけ使う。

**穴の件数 (率の隣に必ず出す)。** abandoned (理由別。`S/store/signals.py:477`)、`no_fill`、`data_insufficient`、未終端、R 不明。あわせて採否の件数 (accept、LLM の reject、回避帯の reject) と、accept のうち risk gate を通った件数。

**少数の表示。** チャートの段と同じ線を使う。母数 5 未満は「–」、5〜29 は「(参考)」、30 以上は通常表示 (30 の根拠は `S/backtest/metrics.py:20,142`)。

**読む経路。** 集計は daemon 側の 1 関数 (純関数 + 読取専用の接続)。既存の `signal_shadow.period_summary` (`S/store/signal_shadow.py:316`、今は呼び出し元が無い) は pips の合計しか返さないので、R の集計は新しい関数にし、`period_summary` は消す。web は戦略別のタブに列を足す。親専有の日次 report (`S/loops/econ_signal_report.py:552`) の shadow 節も戦略別にする (設計 2026-11-01 §2.1 の記述に合わせる)。

### 2.4 週次の確定と判定 (段 3)

**起動。** scheduler の日次 report の hook (`S/core/scheduler.py:450`、登録 `S/service.py:1939`) から呼ぶ。hook は callback を 1 本しか持たない (`:470`) ので、複数を順に呼べるようにする (記録は callback ごとに分け、片方の失敗がもう片方の再試行を起こさない)。週次の callback は取引日が閉じるたびに「直近に閉じた取引週の確定が無ければ作る」を行う。取引週の終わりは、その close から次の開場まで 24 時間以上空く close、週の印はその close の NY の取引日とする。同じ週の確定は表の UNIQUE で 1 回に限る。作れなかった週は次の取引日の close と起動時に再試行される (hook の既存の契約)。直近の 1 週より前は遡って作らない。改善 mission の有無・成否・回数に依らない。集計は SQL と小さな計算だけで、発注の tick を塞がない (既存の日次 report と同じ別 thread)。

**保存。** 新しい表 2 つ (追加だけ、既存の表は変えない)。

- `strategy_review_weekly`: 週の印、name、content_hash、規則の版、最初の採否時刻、N、勝 / 負 / 分、R の利益合計・損失合計、穴の件数、採否の件数、短い窓の件数と R の合計、判定。`UNIQUE(週, name, content_hash)`。金額は持たない (実取引の数字は読むたびにチャートの段の集計から取る)。
- `plugin_inventory_weekly`: 週の印、name、未使用 (0/1)、出所、満たした条件。新しく加わった名前は前の週との差で決める。

**判定 (版ごと、週の確定のたびに 1 回。その時点の採点だけで決まる純関数)。**

1. 長い窓 = 直近 12 週、短い窓 = 直近 4 週。母数は機械採点・全採否の R 既知の件数 (長い窓 N、短い窓 n)。
2. N < 30、または最初の採否から 28 日未満 → `標本不足`。
3. 長い窓の平均 R ≤ 0 → `停止候補`。採用の床 (`improve.gate.min_pf: 1.0` と `require_positive_avg_r`、`config/settings.yaml.example:117-118`) と同じ線である。
4. 長い窓の平均 R > 0 で、n ≥ 10 かつ短い窓の平均 R ≤ 0 → `低下` (全体は床の上だが直近で崩れている)。
5. それ以外 → `維持`。
6. 判定は前の週の判定を読まない。連続する週の長い窓は 11 週ぶん重なるので、「2 週続いたら」は確認にならず 1 週の遅れにしかならないからである。同じ判定が続いた週数は確定の列から数え、表示にだけ使う。
7. 単週の旗: 直近 1 週の件数が 5 以上で R の合計が負なら、report に「今週は負」と書く。判定には使わない (1 時間足の 1 週は約 120 本で、単週の数字に方向を決める力は無い)。

承認時の holdout の成績との比較は判定に使わない (§6 問 2)。report には承認時の数値を並べて出す。

**親専有の週次 report。** `data/improve_reports/` の下の専用 dir に、既存の日次 report と同じ書き方 (owner-only、1 回だけ書く。`S/loops/econ_signal_report.py:779`) で出す。中身は戦略ごとの判定・3 系列の数値・穴の件数・承認時の成績、未使用の指標の一覧、停止済みの plugin の一覧。

**判定が出た後の人間の操作。** 既存の操作だけを使う。提案に「採用」「却下」のボタンは作らない。提案は状態を持たず、次の週にまた計算される。止めれば対象から外れ、止めなければ同じ提案が続く。

### 2.5 通知 (段 3)

改善通知と同じ形にする (設計 2026-10-25 §0.1-3、§4.1)。

- daemon は event `weekly_review_ready` を 1 件出す。fields は週の印 (日付)、停止候補の本数、低下の本数、未使用の指標の本数、新しく加わった本数だけ。名前・数値は event に入れない (event は DB に残り、webhook でも読まれる)。fields の検査は専用の関数で固定する (`S/ops/events.py:54,85` と同じ型)。
- bot は `GET /v1/review/weekly` (`status.read`) で確定の行を読み、本文を作る。読めなければ見出しと本数だけ出す。取得した本文は保持しない。
- 数値は裁定済みの 4 項目 (pf / avg_r / 件数 / 評価不能) に限る。勝率・DD・損益の金額・閾値は載せない。機械採点の値であることを行に書く。
- 知らせる内容が無い週 (停止候補 0、低下 0、新しい未使用 0) は出さない (§6 問 7)。
- 通知の on / off は既存の `ops_notices` に従う (`A/config.py:81`)。新しい設定キーと新しい送信先は作らない。独立 notify (webhook) には event の固定語と本数だけが渡る。

本文の形 (数字は架空):

```text
[週次] 停止の提案 2026-11-21
戦略 (機械採点、直近 12 週)
  <name>: pf 0.82 avg_r -0.11 採点 34 件 — 停止候補 (2 週目)
  <name>: 採点 12 件 (評価不能)
未使用の指標 14 本 (新規 2: <name>, <name>)
確認: afx plugin review / web の plugin 一覧
```

### 2.7 誰に何を見せるか

| 情報 | 人間 (web・CLI・週次 report) | Discord | event・activity・webhook | 改善 agent | 取引 agent・採否 mission・ask・reflection |
|---|---|---|---|---|---|
| 機械採点の数値 (N、勝敗、平均 R、PF) | 出す | 4 項目だけ | 出さない | **出さない** | 出さない |
| 採否・abandoned の件数 (戦略別) | 出す | 出さない | 出さない | 出さない | 出さない |
| 実取引の戦略別成績 | 出す (チャートの段) | 出さない | 出さない | 出さない | 出さない |
| 判定 (標本不足 / 維持 / 低下 / 停止候補) | 出す | 出す | 本数だけ | 段 4: 語だけ (標本不足は `-`)。§6 問 4 | 出さない |
| 続いた週数・単週の旗・窓の長さ | 出す | 続いた週数だけ | 出さない | 出さない | 出さない |
| 未使用の指標 (名前・条件) | 出す | 本数と新規の名前 | 本数だけ | 出さない | 出さない |
| 停止済みの plugin の名前 | 出す | 出さない | 既存の `plugin_disabled` | 段 4: 名前と kind だけ | 出さない |
| 止めた理由・経路、承認・却下の reason | 既存の面だけ | 出さない | 出さない | **出さない** | 出さない |
| 承認時の in_sample / holdout の数値 | 週次 report | 出さない | 出さない | 出さない | 出さない |

守る規律と、その守り方。

- **holdout の数値を agent に見せない。** 前方区間は、次の候補の holdout (今から 3 か月、`S/backtest/holdout.py:69`) にまるごと入る。数値・件数・期間は親のプロセスと人間の面だけに置き、agent へは固定語だけを親が prompt に描く。worker に DB と report の path を渡さない (既存どおり)。
- **人間の reject reason を改善 prompt に漏らさない。** 判定の語と停止済みの名前は、承認・却下の表 (`approval_requests.reason`) と結合せずに作る。停止済みの一覧は「配備の記録 (`plugin_switch_journal` の `decided`) がある名前のうち、今 live でないもの」から作り、disable の actor・再評価の却下・提案の有無を読まない。
- **反応統計の流入を出所で遮断する裁定 (2026-11-07) に触れない。** この設計は reflection・RAG・取引 prompt へ何も足さない。機械採点は signal の保存値と 1 分足だけから決まり、LLM の reasoning を読まない。
- **方向の語は新しい露出である。** 設計 2026-11-01 §3.6 は shadow を改善 agent に渡さないと決め、設計 2026-10-24 §1.2-5・§2.6 は族の表を成績表にしないと決めた。語はこの 2 つの明示の例外になる。`unprofitable` の 1 bit (設計 2026-09-12 §4) と比べると、agent が候補を変えて繰り返し問える oracle ではない (語は配備中の版の live の signal だけで決まり、候補に依らない。変わるのは週に 1 回まで、版が替われば 4 週は `-`)。それでも「この族は前方で負けている」という 1 語は holdout 区間の情報なので、例外として記録し、裁定を得てから入れる。

### 2.8 改善 prompt への掲示 (段 4)

- **停止済みの plugin。** 新しい節「停止済みの plugin」に、名前と kind を昇順で出す。名前は族の表と同じ文法検査 (設計 2026-10-24 §2.3) を通ったものだけ。上限は 50 件・4 KiB、超えた分は `他 N 件を省略`。節の文面は固定で、「ここにある名前と同じ仮説を別名で作り直さないでください。理由は示しません」とする。戻す道は人間の操作だけである (`afx plugin rollback <name> --to <hash>` で live に戻せば一覧から消える)。未使用として外した指標を agent が自分で作り直す道は閉じるので、外す判断は「今後も材料にしない」ものに限る旨を提案の文面と運用文書に書く。
- **方向の語。** 族の表の `deployed` 列の名前の後ろに付ける (`yes (<name>: 低下)`)。列は増やさない (行末の形と byte 予算の pin を保つ。設計 2026-10-24 §2.5)。語は直近の確定から取り、確定が 3 週より古ければ `-` にする。節の文面に「`低下` / `停止候補` は配備後の成績の方向だけを示します。数値はありません。`停止候補` の族を土台にした更新は、仮説のどこを変えるかを説明してください」を足す。
- 語を描く関数は、判定の語 1 つだけを引数に取る。確定の行そのもの (数値を含む) を改善 context の組み立てに渡さない。

## 3. 失敗時・運用

| 事象 | 動き |
|---|---|
| 週次の集計が例外・DB busy | その週は作らない。週の印を進めず、次の日次 hook と起動時に 1 回ずつ再試行する。取引・改善は止めない |
| report の書込み失敗 | 確定の行は残す。通知は出す (本文は API から読む)。status に失敗を出す |
| bot が本文を取れない | 見出しと本数だけ出す |
| 確定が古い (直近 3 週に無い) | web・CLI は「確定が古い」と日付を出す。agent の語は `-` |
| shadow の slice worker が滞る (未終端が増える) | 未終端の件数を穴として出す。母数が減り `標本不足` に倒れる (誤って停止候補にしない側) |
| 版が替わった・rollback した | 新しい版は数え直し。rollback で戻った版は、その版の過去の採点を窓の中で数える |
| 戦略が週の途中で止まった | 対象から外す。確定の行は消さない |
| plugin の scan が失敗 | 棚卸しは「判定できない」と出し、未使用 0 本とは書かない |
| チャートの段の集計が読めない | 実取引の列だけ「読めません」。機械採点と判定は出す |
| DB の表が旧版 (新しい表が無い) | 読取面は「未確定」を返す。起動時の表の作成は既存の追加の慣行に従う |

## 4. test と受入

### 足す test

1. **未使用の判定**: 条件 1〜4 の全組合せ、人間の出所、保留中の依頼の参照、族の key に名前が出る / 出ない、K の境界、scan 失敗。
2. **R の集計**: long / short、R 不明の各原因、`no_fill`・`data_insufficient`・未終端を母数に入れない、PF と平均 R の符号の一致、版の分離、窓の境界 (採否時刻)。fixture は本番の shadow 行の形から作る。
3. **判定**: (長い窓の母数と符号 × 短い窓の母数と符号 × 最初の採否からの日数) の表を 1 本の test で全数。30 件・10 件・28 日・平均 R = 0 の境界。前の週の確定を変えても今週の判定が変わらないこと。
4. **週の確定**: 取引週の最後の close で 1 回だけ、同じ週の 2 回目は作らない、起動時の追いつき、冬時間・夏時間の実時刻の例 (金曜 NY 17:00 = 21:00Z / 22:00Z)、休場をはさむ週。
5. **event と通知**: fields が固定語と整数だけ (名前・小数を拒否)、本文の 4 項目、内容の無い週は出さない、API が読めないときの縮退。
6. **遮断の回帰**: 改善 context と描いた prompt の全文に、確定の数値・件数・続いた週数・週の印・未使用の本数・disable の actor・reason が現れない。語は 3 語と `-` だけ。停止済みの節は名前と kind だけ。判定の関数を「数値を返す」ように変えた変異で test が落ちることを確かめる。
7. **CLI**: help が `cli_surface.py` から出る (literal 検査)、`afx plugin review` が daemon なしで読める。

### 受入 (利用者、本番)

1. web の plugin 一覧で「未使用」に絞り、手で 3 本を選んで参照元・候補への登場が無いことを確かめる。
2. 戦略別のタブで、機械採点の件数が DB の shadow の件数と一致する。穴の件数が出ている。
3. 取引週の終わりに週次 report ができ、Discord に (内容があれば) 1 通届く。数値が 4 項目だけである。
4. 改善 mission の prompt の記録に、数値が無く語だけがある (段 4)。

## 7. 残余・やらないこと

- **abandoned の signal の採点**: しない。採否の 3 正規形と shadow の外部キーを変える必要があり、採否の契約に触れる。穴の件数として見せる。配備中の 1 本で約 4 割が該当するので、機械採点は「鮮度内に採否できた signal」に偏る。原因 (鮮度切れ) の是正は別の課題である。
- **自動停止・自動 disable・削除**: しない。
- **戦略ごとの枠・実帳簿**: `per-strategy-virtual-books` のまま。段 2 が着手条件を測る面になる。
- **日次の改善との兼ね合い**: 週の確定は mission と独立なので、`improve-daily-params-weekly-algorithm` が入っても変えない。
- **同名更新か新名かの方針・保有上限**: `plugin-naming-lifecycle-policy` のまま。停止済みの節は方針が決まるまでの抑止である。
- **機械採点の偏り**: spread は採否時の 1 点、swap・手数料なし、同時に何本でも建つ前提。表示の固定文で伝える。
- **判定の誤差**: 30〜100 件では平均 R の符号そのものが偶然で入れ替わり得る。床の線の近くでは週ごとに `維持` と `停止候補` が入れ替わることがある。判定は提案であり、止める前に `reevaluate` で履歴の成績を確かめる手順を運用文書に書く。
- **人間が通知の数値を方針や backlog に書き写す**: 防げない。運用文書の既存の注記 (holdout の数値を方針に書かない) の対象に週次の数値を足す。
